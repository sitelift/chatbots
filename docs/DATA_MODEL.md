# Data Model

SiteLift Chatbots stores everything in a single SQLite database. This document defines the schema. It is a design spec; the exact SQL will be implemented later.

## Overview

Three core tables:

- **chatbots** — one row per website chatbot. Holds identity, configuration, the business-facts system prompt, and the (encrypted) AI API key.
- **conversations** — one row per visitor thread, belonging to a chatbot.
- **messages** — the individual user/assistant turns within a conversation.

### Key relationships

```
chatbots 1 ──── * conversations 1 ──── * messages
```

## Table: `chatbots`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | TEXT (PK) | Public id, e.g. `ch_abc123`. Random, unguessable. |
| `name` | TEXT | Display name, e.g. "Acme Support Bot". |
| `website_url` | TEXT | The target website this bot serves (informational / used for origin matching if enabled). |
| `welcome_message` | TEXT | First message shown in the widget panel. |
| `brand_color` | TEXT | Hex color used by the widget (e.g. `#0f172a`). |
| `business_facts` | TEXT | **The system prompt body.** Free-form English business facts. |
| `model` | TEXT | Provider model id, e.g. `gpt-4o-mini`. |
| `base_url` | TEXT | OpenAI-compatible API base, e.g. `https://api.openai.com/v1`. |
| `api_key_encrypted` | TEXT | Encrypted API key. **Never stored in plaintext.** `NULL` if not set. |
| `api_key_hint` | TEXT | Last 4 chars of the key, for display ("•••• abcd"). `NULL` if unset. |
| `temperature` | REAL | Default `0.7`. |
| `max_tokens` | INTEGER | Default `512`. |
| `enabled` | INTEGER (bool) | `1` = active (serves chat), `0` = disabled (widget shows offline). |
| `created_at` | TEXT (ISO-8601) | |
| `updated_at` | TEXT (ISO-8601) | |

### Notes on `id`

- Generated as a random token (e.g. 22-char base62) so it is not enumerable by sequential guessing.
- Used directly in the embed snippet (`data-chatbot-id`) and in public URLs.

### Notes on `api_key_encrypted` / `api_key_hint`

- The key is encrypted with AES-256-GCM using the server's `ENCRYPTION_KEY` (see [SECURITY.md](SECURITY.md)).
- Only the *encrypted* blob and a short hint are stored. The plaintext key exists only in memory, for the duration of an AI call.
- Admin API responses always redact this — the client never receives the key back.

## Table: `conversations`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | TEXT (PK) | Public id, e.g. `cv_xyz789`. Random. |
| `chatbot_id` | TEXT (FK → chatbots.id) | Owning chatbot. |
| `visitor_id` | TEXT | Anonymous id generated by the widget, stored in the visitor's `localStorage`. |
| `status` | TEXT | `open` / `closed` (reserved for future lead-capture states). Default `open`. |
| `visitor_name` | TEXT | Captured name, if the visitor volunteers it during the chat (see ARCHITECTURE §8). `NULL` if unknown. |
| `visitor_email` | TEXT | Captured email, if the visitor volunteers it. `NULL` if unknown. |
| `created_at` | TEXT (ISO-8601) | |
| `updated_at` | TEXT (ISO-8601) | |

### Notes

- A **visitor** is identified by an anonymous `visitor_id`, not by any account. Multiple conversations can share a `visitor_id`; the widget typically resumes the most recent one.
- A conversation belongs to exactly one chatbot. The chat endpoint must verify that a supplied `conversationId` belongs to the chatbot in the URL.
- `visitor_name` / `visitor_email` are **volunteered**, never collected via a forced form. The AI asks naturally; the visitor may decline (see ARCHITECTURE §8).

## Table: `messages`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | TEXT (PK) | Public id, e.g. `msg_abc`. Random. |
| `conversation_id` | TEXT (FK → conversations.id) | Parent conversation. |
| `role` | TEXT | `user` or `assistant`. |
| `content` | TEXT | The message body. |
| `created_at` | TEXT (ISO-8601) | |

### Notes

- Messages are append-only. Editing/deleting is an admin function only (future).
- The **system prompt is not stored as a message row.** It is derived from the chatbot's `business_facts` and injected at request time. This means editing facts retroactively affects past-context responses only going forward — a deliberate, simple behavior.

## Conversation context window (history sent to the AI)

Each turn, the server sends the AI:
1. The system message (built from `business_facts`),
2. The **most recent** messages in the conversation, capped.

**v1 cap: the last 20 messages** (10 exchanges). Rationale:

- Keeps token usage bounded and predictable.
- Doubles as **abuse prevention** — a single visitor cannot build an unboundedly expensive thread.
- Simple to implement — a single `LIMIT 20` query ordered by `created_at DESC`.

> **Settled:** the 20-message cap is the v1 decision. Token-count-based capping was considered and rejected for simplicity. Related abuse-prevention defaults (max message length 2000 chars, ~20 msgs/min per visitor) are documented in [ARCHITECTURE.md §7](ARCHITECTURE.md#7-abuse-prevention).

## Indexes

- `idx_conversations_chatbot (chatbot_id)` — fast lookup of a chatbot's conversations.
- `idx_messages_conversation (conversation_id, created_at)` — fast history retrieval for the context window.

## Migration approach

v1 uses a simple schema-creation-on-startup approach: `CREATE TABLE IF NOT EXISTS` statements run at boot. Schema *changes* in later versions are applied via a small, ordered migration list (array of SQL scripts with a `schema_version` table). For v1, plain `IF NOT EXISTS` is sufficient.
